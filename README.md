# 👻 Бюро переселения привидений

Веб-приложение для оператора бюро, которое подбирает привидениям из старых домов
новое место обитания: замок, маяк, библиотеку, заброшенный театр, подвал старой
типографии и так далее — с объяснением решения, обработкой конфликтов и ручной
корректировкой выбора.

- **Backend:** Python, FastAPI, PostgreSQL, SQLAlchemy (async), Alembic, `uv`
- **Frontend:** чистый HTML/CSS/JavaScript (без фреймворков), раздаётся отдельным nginx
- **Упаковка:** Docker Compose (Postgres + backend + nginx + одноразовые сервисы миграций и сида) —
  приложение запускается только так, отдельного способа запустить его без Docker нет
- **AI Worklog:** отдельная вкладка внутри самого приложения ("AI Worklog" в навигации)

> Ссылка на публично развёрнутое приложение: **пока не задеплоено** — на этом этапе
> проект осознанно запускается только локально (см. вкладку AI Worklog, раздел
> "Решения, принятые разработчиком самостоятельно").

## Быстрый старт (Docker — рекомендуется)

Понадобится только Docker и Docker Compose.

```bash
cp .env.example .env      # секретов внутри нет — это локальная демо-база
docker compose up --build
```

После старта:

- приложение (фронтенд, раздаётся nginx) — http://localhost:8080
- API напрямую и документация API (Swagger) — http://localhost:8000 и http://localhost:8000/docs
- Postgres — localhost:5432 (логин/пароль из `.env`)

Перед стартом `backend` и `nginx` `docker compose` поднимает два одноразовых сервиса:

1. `migrate` — применяет миграции Alembic и завершается.
2. `seed` — после успешного завершения `migrate` проверяет, есть ли уже данные в базе
   (`backend/seed_data/run_seed.py`), и заполняет её демонстрационными данными, только
   если её нет. Если `SEED_DEMO_DATA=false` в `.env`, сервис ничего не делает.

`backend` стартует только после того, как оба этих сервиса успешно завершились
(`depends_on: ... condition: service_completed_successfully`), а `nginx` — после
`backend`, и проксирует `/api/` на него (см. `nginx/nginx.conf`), а остальное отдаёт
как статику из `frontend/`.

Демонстрационные данные покрывают все обязательные сценарии из ТЗ (см. чек-лист ниже).

Остановить и удалить контейнеры вместе с volume базы:

```bash
docker compose down -v
```

Приложение запускается **только через Docker Compose** — отдельного режима "без
Docker" для самого приложения (backend + frontend вместе) больше нет.

**Важно:** backend собирается в Docker-образ (`build:` в docker-compose.yml), а не
подключается как volume с живым кодом. Значит после любых правок в `backend/*.py`
одного `docker compose up` недостаточно — нужно пересобрать образ:

```bash
docker compose up --build
```

Без `--build` Compose может решить, что образ не изменился, и продолжит работать
со старым кодом внутри контейнера, даже если файлы на диске уже обновлены.

## Логи

Backend логирует через [loguru](https://github.com/Delgan/loguru) — и в консоль
(`docker compose logs -f backend`), и в файл `backend/logs/app.log` на хосте
(папка проброшена как volume, файл можно открыть в любом редакторе, не заходя в
контейнер). Там видно каждый входящий запрос (`--> POST /api/match/run` /
`<-- ... -> 200`) и ключевые события бизнес-логики: сколько заявок обработано,
сколько назначений создано/удалено, любые исключения при `commit()`. Уровень
логирования регулируется переменной `LOG_LEVEL` в `.env` (по умолчанию `INFO`;
`DEBUG` добавляет построчный разбор каждого подбора места).

## Тесты

Тесты — единственное, что можно (и стоит) гонять без полного `docker compose up`,
локально через `uv` (зависимости объявлены в **общем `pyproject.toml` в корне
репозитория**, а не внутри `backend/`):

```bash
uv venv
uv pip install -e ".[dev]"
uv run pytest -v
```

- `backend/tests/test_matching.py` — юнит-тесты алгоритма подбора (без базы данных).
- `backend/tests/test_api.py` — интеграционные тесты API поверх SQLite в памяти (реальный Postgres не нужен).

Через Docker:

```bash
docker compose run --rm backend pytest -v
```

> Честно: в песочнице, где собирался этот проект, не было доступа к PyPI, поэтому
> `pytest` там не запускался ни разу — подробности в вкладке AI Worklog. Обязательно
> прогоните тесты сами перед сдачей.

## Как работает алгоритм подбора

1. **Жёсткие условия** (место отбрасывается полностью, если нарушено хоть одно):
   - в месте нет свободных мест (переполнено);
   - дедлайн переселения уже прошёл;
   - привидению нужен чердак, а в месте его нет;
   - привидение боится зеркал, а в месте они есть;
   - привидению нельзя жить рядом с людьми, а в месте они бывают;
   - привидению нужна темнота, а в месте ярко;
   - привидению нужна тишина, а в месте шумно.
2. **Мягкий рейтинг 0–100** для мест, прошедших жёсткие условия — взвешенная сумма
   близости температуры, соответствия шума уровню тревожности, влажности и тесноты.
   У каждого варианта — текстовое объяснение по-русски.
3. **Пакетный подбор** обрабатывает заявки по срочности (ближайший дедлайн →
   выше тревожность), чтобы более срочные и тревожные привидения не остались без
   места из-за того, что его заняли менее срочные заявки.
4. **Кнопка «Обновить предложения» реально назначает места** — каждой ещё не
   распределённой заявке она присваивает лучший найденный вариант и сразу
   сохраняет это в базу (тег «⚙ Назначено автоматически»). Уже существующие
   ручные назначения (тег «✋ Ручной выбор») кнопка не трогает и не пересчитывает.
   Заявкам, которым место не нашлось ни при каких условиях, ставится тег
   «✕ Автоматически не получилось» — им место можно подобрать только вручную.
5. **Оператор может переназначить вручную** в любой момент — кнопкой «Выбрать
   вручную» с любым местом из списка на карточке заявки. Выбор проходит ту же
   проверку жёстких условий (заблокировать нельзя обойти) плюс мягкие
   предупреждения, которые можно осознанно подтвердить.

Код алгоритма: `backend/app/services/algorithm.py` — чистые функции без обращения к
базе (принимают обычные объекты `app.db.models.Ghost`/`Location`, но не трогают сессию),
поэтому их легко тестировать и переиспользовать.

## Архитектура backend'а

Три слоя, как и договаривались, плюс отдельные пакеты для инфраструктуры и контракта API:

- **`app/repositories/`** — только доступ к данным (SELECT/INSERT/DELETE через
  SQLAlchemy). Ничего не знает о бизнес-правилах и никогда не коммитит транзакцию.
- **`app/services/`** — бизнес-логика: решает, что делать, вызывает один или
  несколько репозиториев, владеет границей транзакции (`commit`). Здесь же —
  чистый алгоритм подбора (`services/algorithm.py`), у которого вообще нет
  зависимости от базы данных.
- **`app/routers/`** — тонкий HTTP-слой: принимает запрос, вызывает нужный сервис,
  переводит его исключения (`NotFoundError` и т.д.) в HTTP-коды.
- **`app/db/`** — всё, что касается хранения: ORM-модели (`models.py`), engine и
  сессия SQLAlchemy (`session.py`), общий словарь enum'ов (`enums.py`). Единственный
  источник истины о структуре данных; отдельного набора dataclass-моделей для
  алгоритма больше нет — отказались от дублирования, сервисы и алгоритм работают
  напрямую с ORM-классами.
- **`app/schemas/`** — контракт API: Pydantic-схемы запросов/ответов, разложенные
  по сущностям (`ghost.py`, `location.py`, `matching.py`, `report.py`).
- **`app/core/`** — общие настройки проекта (`config.py`), не привязанные к
  конкретному слою.

`app/main.py` теперь занимается только сборкой FastAPI-приложения и API — никакой
логики заполнения базы или раздачи фронтенда в нём больше нет. Заполнение демоданными
вынесено в отдельный скрипт `seed_data/run_seed.py`, который запускается как отдельный
одноразовый сервис `seed` в docker-compose (после `migrate`), а не при каждом старте
backend'а. Раздача фронтенда тоже вынесена из backend'а — этим занимается отдельный
сервис `nginx` (см. "Быстрый старт" выше и `nginx/nginx.conf`).

## Структура проекта

```
pyproject.toml            # общие зависимости проекта (uv) — один на весь репозиторий
.env.example                # единый .env-шаблон для Docker и локального запуска (см. "Секреты")
backend/
  Dockerfile
  alembic.ini
  app/
    core/
      config.py            # настройки проекта (читаются из переменных окружения)
    db/
      session.py             # engine, сессия SQLAlchemy, FastAPI-зависимость get_db
      models.py                # ORM-модели (Ghost, Location, Assignment)
      enums.py                  # общий словарь enum'ов (освещение, влажность, особые условия)
    schemas/
      ghost.py, location.py, matching.py, report.py   # Pydantic-схемы по сущностям
    repositories/      # доступ к данным: GhostRepository, LocationRepository, AssignmentRepository
    services/           # бизнес-логика + алгоритм подбора (algorithm.py, matching_service.py, ...)
    routers/             # тонкие эндпоинты FastAPI (ghosts, locations, matching, report)
    main.py                # сборка приложения и API, обработка ошибок
  seed_data/
    seed.py               # демонстрационные данные + seed_if_empty()
    run_seed.py             # точка входа одноразового сервиса seed в docker-compose
  alembic/                 # миграции базы данных
  tests/                    # юнит- и интеграционные тесты
frontend/
  index.html
  css/styles.css
  js/api.js             # обёртка над fetch с обработкой ошибок
  js/app.js              # вся логика интерфейса
  js/worklog-content.js   # текст вкладки AI Worklog
nginx/
  nginx.conf               # раздача frontend/ + проксирование /api/ на backend
docker-compose.yml
```

## Секреты

В коде и в образе секретов нет. Есть один общий `.env` в корне репозитория (см.
`.env.example` там же) — им пользуется и `docker-compose.yml` (пароль Postgres и
остальные переменные для контейнеров), и `app/core/config.py` при запуске тестов
локально (находит этот файл по абсолютному пути независимо от того, откуда запущен
процесс). Отдельных `.env`/`.env.example` внутри `backend/` или `frontend/` больше нет.
`.env` в git не попадает (`.gitignore` уже исключает `.env`).

## Чек-лист проверки перед сдачей

Обязательные состояния из ТЗ и как их проверить на демо-данных (загружаются сервисом
`seed` при первом `docker compose up --build`, `SEED_DEMO_DATA=true` по умолчанию):

- [ ] **Пустой список заявок** — удалите все заявки на вкладке «Заявки» (или поднимите
      базу с нуля через `docker compose down -v`, `SEED_DEMO_DATA=false` в `.env`,
      `docker compose up --build`) и убедитесь, что вкладки «Заявки» и «Подбор»
      показывают дружелюбное сообщение, а не пустой экран или ошибку.
- [ ] **Заявка без подходящего места** — демо-привидение «Барон фон Скрип» требует
      чердак и боится зеркал одновременно: единственное место с чердаком (замок) —
      с зеркалами. Запустите подбор и убедитесь, что причина невозможности показана
      понятно.
- [ ] **Место переполнено** — демо-место «Городская библиотека» изначально занято
      полностью (3/3). Убедитесь, что она не предлагается как вариант и что при
      попытке вручную назначить туда кого-то приложение блокирует выбор с причиной
      «переполнено».
- [ ] **Ручной выбор конфликтует с условиями** — два варианта на вкладке «Подбор»:
      1) мягкий конфликт: назначьте «Эхо Библиотекарь» (любимая температура 19°C)
      вручную в «Подвал старой типографии» (10°C) — появится предупреждение о
      сильном расхождении температуры и кнопка «Всё равно назначить»;
      2) жёсткий конфликт: попробуйте вручную назначить кого угодно в переполненную
      «Городскую библиотеку» (3/3) — приложение заблокирует выбор без возможности
      продавить, с явной причиной «переполнено».
- [ ] **Понятное сообщение об ошибке** — временно остановите контейнер `db`
      (`docker compose stop db`) и обновите любую вкладку: интерфейс должен показать
      баннер с понятным текстом, а не зависнуть или показать сырой traceback.
      Верните `docker compose start db`.

Дополнительно вручную проверено (можно дополнить своими сценариями):

1. Создание новой заявки и нового места через формы — появляются в списках сразу
   после сохранения.
2. Запуск подбора несколько раз подряд — результаты пересчитываются, ручные
   назначения не сбрасываются.
3. Снятие назначения («Снять назначение») и повторный подбор — привидение снова
   участвует в автоматическом распределении.
4. Финальный отчёт корректно считает расселённых/нерасселённых и показывает
   перегруженные места (загрузка ≥ 80%).
5. Удаление заявки/места — связанные назначения корректно снимаются, вместимость
   пересчитывается.
